TransitionFunctionIteration Objects

OutputVaultTFIExt stores the types of TransitionFunctionIteration.jl. It loads when TransitionFunctionIteration, StaticArrays and StructArrays are loaded. TFI itself writes no files: it defines Tables.jl interfaces and metadata for its result types, and this extension writes them with the project's table format.

Every object records its storage kind (for example TransitionFunctionIteration.SimulationPanel) in its file, and load restores the object as that type.

Solutions and steady states

The portable solution file holds plain HDF5-compatible arrays and metadata, with no Julia objects, so it reads without the code that wrote it, in Python with h5py for example. Files are written uncompressed because h5py cannot read JLD2's compressed datasets. Layout, schema version 2:

outputvault/kind                         storage kind
meta/{schema_version, tfi_version, created, solution_id, model_type, singletons}
meta/model/...                           the model's metadata (model_metadata)
meta/provenance/<key>                    strings from the caller (the git commit id)
grid/<axis>, grid/__axes                 grid vectors (a singleton axis has length 1) and their order
exogenv/points/<var>, .../__names        the exogenous states' values and their order
exogenv/mtrans, exogenv/ssidx            transition matrix and steady-state index
Pfct/<var>, Vfct/<var>, Ffct/<var>       arrays over the grid axes (Pfct in unconstrained space)
Tfct/<var>                               arrays over the grid axes and next period's exogenous state
<fct>/__vars                             variable order
Pfct/__bounds/<var>, Tfct/__bounds/<var> [lower, upper], plus __names

A steady-state file has meta/..., the model's metadata, and guess/, endog/, exog/, values/ (one entry per name plus __names). It does not store the model: a steady state takes its model from the solution file in the same folder.

The schema version is an integer that changes only when a change breaks readers of earlier files; the reader accepts only the current version, and added entries do not change it.

Rebuilding the model

A portable solution stores the model's metadata, the model's fields as plain data: model_metadata(mdl) keeps reals, strings, symbols and numeric arrays and tuples with at most 1000 elements, recursively through structs and named tuples to depth 4, and drops everything else (functions, interpolants, large arrays). Loading needs a way back to a model:

load(rf, :solution; solution_format = :portable, model = mdl)         # an instance: checked against the metadata
load(rf, :solution; solution_format = :portable, model = MyModel)     # a type: rebuilt from the metadata

The default rebuild is MyModel(; metadata...). A model package whose models need more (derived objects that were dropped, nested parameter structs) overloads model_metadata and model_from_metadata for its type. The solution id (solution_id in TFI), a hash of the grid and the values of the functions, is stored and checked on load, and a mismatch warns that the file may be corrupted.

Tables

TFI's tables carry their own metadata (tfi.kind, tfi.rowkey, tfi.endog, tfi.provenance), and OutputVault adds its storage kind (outputvault.kind); both are in the file's metadata, so TFI's constructors restore the right type. TFI's tables restore as their own types only from table formats that keep file-level metadata (Parquet does).

A MomentArray is written with the row names in the column named by its row key: variable for moments, equation for error statistics, parameter for parameters. Moments by sample (describe(...).moments) are one file per sample, in the order they were saved, which is recorded in each file's metadata so that load returns them in order.

Parameters and recursions

save_result(rf, (; params = collect_parameters(obj)))

collect_parameters turns the model's scalar parameters (every real or Boolean field, a Boolean as 0 or 1) into a one-column MomentArray with row key parameter, which is what the params component holds and what a DuckDB query returns as vault_params. A model package can define its own method to choose differently.

The recursions component holds interpolants over the solution's grid, one file each, for quantities computed at the solution's policies after the solve. The file holds its own grid, so it loads without the solution, and saving one never touches the solution folder.

Comparing saved runs

using TransitionFunctionIteration
compare_economies(moments, (base = RunHandle("base"), alt = RunHandle("alt")))

compares moments (see TFI's guide on moments) across runs read with the active configuration: each run's stats, and its IRFs if a moment is an ImpulseMoment. For queries over many runs, assemble_moments reads only the statistics that the moments need, in one DuckDB query (Querying with DuckDB).
