API Reference

Runs and configuration

OutputVault.RunHandle — Type
RunHandle(economy; branch=current_branch(), experdef="default")
RunHandle(; branch, experdef, economy)

Identifies a saved run by branch, experiment definition, and economy name. The run's folder is <output_root>/<branch>/res-<experdef>-<economy>.

branch defaults to the git branch of Julia's working directory. Passing it chooses only the folder: the git commit saved with a solution is always that of the working directory's repository.

All fields are coerced to String on construction. experdef must not contain -: the run's folder is res-<experdef>-<economy>, and readers (the DuckDB macros in outputvault.sql) split it at the first hyphen. economy may contain anything.

source
OutputVault.Config — Type
Config(; output_root, table_format=nothing, solution_format=(:portable, :native),
         staging_root=joinpath(tempdir(), "OutputVault"))

A project's OutputVault settings. Where each object goes is fixed (LAYOUT); which objects are saved is chosen in each save_result call.

Arguments

  • output_root: filesystem root for all saved outputs.
  • table_format: an AbstractTableFormat (e.g. OutputVault.Formats.ParquetFormat()), needed to save objects written as tables (TFI's simulations, moments and IRFs).
  • solution_format: how the solution is saved: :portable (one file per object, written by the package that supports its type; for TFI a documented layout of plain arrays; JLD2 for other values), :native (all of the solution's objects in one JLD2 file, res.jld2, as Julia objects), or both. Other components are saved one file per object, like the portable copy.
  • staging_root: where save_result writes a new solution's run folder before moving it into place. If the move fails (on Windows, open files can block it), the new results stay here and save_result warns. Default: a folder in the system temp directory.

OutputVault.LAYOUT — Constant
LAYOUT

Where each saved property goes: one folder per component under the run's folder. Fixed, so that every project's runs have the same structure and tools can find objects across runs.

componentproperties
solutionobj, stv
statsstats (the moments compare_economies compares; moments by sample are saved one table per sample, stats/<sample>.<ext>)
errstatserrstats
simulationsimseries, errs
irfirf
paramsparams (the model's scalar parameters, see TFI's collect_parameters)
recursionsclaims, welfare (interpolants of recursions computed at a solution's policies; each is saved when it is computed, the solution is not touched)

Saving and loading

OutputVault.save_result — Function
save_result(cfg::AbstractConfig, rf::RunHandle, result; dirty_repo_check) -> String
save_result(rf::RunHandle, result; kwargs...) -> String

Save the properties of result that LAYOUT names, each in its component's folder under the run's folder for rf, one file per property. Which objects are saved is the caller's choice: properties that result lacks or that are nothing are not saved; properties outside the layout are ignored. Each object is written by the package that supports its type (write_object), or with JLD2 as a Julia object.

A save that includes obj or stv makes a new run folder holding only what it saves. It writes the new results to a folder in staging_root(cfg), renames the existing run folder (if any) aside, moves the new folder to the run's path, and deletes the old one. Everything saved for the run before is then gone, including an obj when only stv is saved. It returns the folder holding the new results: the run's path, or, if a rename or move failed (on Windows, open files can block them), the staging folder, with a warning that says where the new and the old results are. If only the final delete fails, the new results are in place and a warning names the old folder to delete. Check the return value before relying on the run's path.

A save without obj or stv (e.g. IRFs computed later) writes into the existing run folder, replacing objects of the same name, and is an error if the run was never saved. It returns the run's folder.

The solution is saved in the formats solution_format(cfg): :portable writes one file per object, :native writes all its objects to res.jld2 with JLD2. The solution folder also receives the git commit id (git_commit.txt) of the repository containing Julia's working directory and, for a dirty repository, the staged and unstaged diffs (git_staged.diff, git_unstaged.diff; the latter includes untracked files). Solution objects get the commit id as provenance.

Keyword arguments

  • dirty_repo_check: :warn (default), :error, or :ignore. Controls behavior when the repository has uncommitted changes. It applies only to saves that include solution objects: other saves record no git state and do not check the repository.

FileIO.load — Function
load(cfg::AbstractConfig, rf::RunHandle, component::Symbol; solution_format = :native, model = nothing) -> NamedTuple
load(rf::RunHandle, component::Symbol; kwargs...) -> NamedTuple

Load a saved component (see LAYOUT) and return a NamedTuple of the properties that were saved, in layout order. Objects come back as their own types (e.g. a TFI ModelSolution or SimulationPanel). The no-config form uses the module-level config.

For the solution, solution_format picks the copy that is read: :native (res.jld2, the objects as Julia saved them; needs compatible code) or :portable (one file per object). Portable TFI solutions and steady states need model: a model instance, whose parameters are compared with the saved ones, or a model type, rebuilt from them (see load_solution). Other components have one copy and ignore both keywords.

save_solution(path, obj; provenance = Dict{String,String}())

Write a model solution to a single portable HDF5-compatible file of plain data. Finding runs

OutputVault.find_matching_results — Function
find_matching_results(cfg::AbstractConfig, wildcard = "$(current_branch())/res-*"; key = (:branch, :experdef, :economy))
find_matching_results(wildcard = ...; kwargs...)

The saved runs whose folders match wildcard, a glob relative to the output root, as a NamedTuple of RunHandles. Folders whose names are not of the form res-<experdef>-<economy> are skipped.

Each run is named by key: the run's branch, experdef and economy joined with __, or only the fields you pass (key = :economy, key = (:experdef, :economy)). Characters other than letters, digits and _ become _, so that feature/x is feature_x. If two runs get the same name, it is an ArgumentError that lists them.

Table formats

OutputVault.AbstractTableFormat — Type
AbstractTableFormat

How tables (simulations, moments, IRFs) are stored. A format implements table_extension(fmt), write_table_file(fmt, path, table, meta) (write the table with its own metadata plus the file-level entries meta, a Dict{String,String}) and read_table_file(fmt, path) (a Tables.jl source whose file metadata DataAPI.metadata reads). Built-in formats are in OutputVault.Formats, with their methods in package extensions; TableFormat takes the functions directly.

source
OutputVault.Formats — Module

Built-in table formats. Each needs its IO package loaded (using Parquet2 for ParquetFormat), which loads the package extension that implements it.

The producer interface

For extensions that store the types of a package (Writing an Extension).

OutputVault.storage_kind — Function
storage_kind(x) -> Union{String, Nothing}

The kind OutputVault records with x, which selects the read_kind method that restores it. Producers define it for their types, namespaced by package (e.g. "TransitionFunctionIteration.ModelSolution"). Default nothing: stored with JLD2 as is.

source
OutputVault.write_object — Function
write_object(cfg, dir, name, x; provenance)

Write x into dir as name.<ext>. Producers add methods for their types, built on write_table or jld2_record so that the kind is recorded. Without a method for its type, an object (a Tables.jl table included) is saved with JLD2 as a Julia object, name.jld2. provenance holds strings identifying the run (the git commit id, for objects of the solution).

source
OutputVault.write_table — Function
write_table(cfg, stem, table; meta = Dict{String,String}())

Write a Tables.jl table as stem.<ext> with the config's table format, recording storage_kind(table) and the entries meta in the file's metadata.

source
OutputVault.write_table_parts — Function
write_table_parts(cfg, dir, name, parts::NamedTuple)

Write object name, a NamedTuple of tables, as one table per part, dir/<part>.<ext>. Each file records the object it belongs to and its position, so that loading returns the NamedTuple with its parts in order. Producers use it for objects such as moments by sample.

The storage kind recorded in a JLD2 file, or nothing.

OutputVault.assemble_moments — Function
assemble_moments(root, moments; branch = "**", experdef = "*", economies = nothing, parameters = true) -> NamedTuple

Select from the saved runs under the output root root the numbers that moments (a NamedTuple of TransitionFunctionIteration moments) need, with DuckDB (vault_stats, vault_irf and vault_params). Returns a column table with one row per (run, number): branch, experdef, economy, kind (simulation, impulse or parameter), group, variable, stat, period and value, all names Strings. This is the form for any language to read; split_by_economy turns it into what TFI's getmoment and compare_economies read.

branch and experdef are glob patterns that select the runs (by default all branches and experdefs); economies is an optional list of economy names to keep. DuckDB opens the files of the components it reads in every selected run, which downloads online-only files in a synced folder, so select only the runs you need. A run without the component of a kind of number (statistics, IRFs or parameters) has no rows of that kind; the table is empty if no run has any.

parameters selects the saved model parameters (the params component) that are added as rows (kind = "parameter", group = "parameters", stat = "value", period = 0): true (the default) for all, false for none, or a collection of names. Parameters that a ParameterMoment among moments names are always included. Needs DuckDB, Tables and TransitionFunctionIteration loaded (it is implemented in a package extension).

source
OutputVault.split_by_economy — Function
split_by_economy(table; key = (:branch, :experdef, :economy), order = nothing) -> NamedTuple

The long table of assemble_moments as one Dict per run, in a NamedTuple. Each Dict maps a row (kind, group, variable, stat, period), with Symbols, to its value, and is a source that TFI's getmoment reads for any moment; the NamedTuple is the economies argument of getmoment(economies, moment, economy, base) and compare_economies.

Runs are named by key: the run's branch, experdef and economy joined with __ by default (main__v1__base), or only the fields you pass (key = :economy gives base). Characters other than letters, digits and _ become _. Distinct runs that get the same name are an ArgumentError that lists them: select fewer runs in assemble_moments or use a longer key.

order lists the names to keep, in that order; the first is the base of a comparison. A name not in the table is an error. Without order, runs come in the order of the table. Duplicate rows within a run are an error.

source
OutputVault.momentrows — Function
momentrows(moment)

The rows of the long table of assemble_moments that a TFI moment needs, as NamedTuples (kind, group, variable, stat, period) of Symbols and an Int: the first is the moment's value and a second, for an impulse moment whose transformation requires it, the path named by its basis (:uncond by default). Level moments need only the first row. A calculated moment needs the rows of its inputs.
